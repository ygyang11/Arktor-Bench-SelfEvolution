## Prompt

### Scenario

Four mobile robots search a bounded indoor area for a chemical source. Each robot can measure odor concentration and a local spatial gradient, but the source position itself is unknown to the control policy. The robots send selected observations to a base station over delayed and lossy uplinks. The base station can service only one queued report per slot, fuses recent reports into a source estimate, and returns motion commands after a downlink delay. Old or redundant reports consume the limited reporting budget without necessarily improving the estimate, while sparse communication can leave the robots following only local information and prevent a supported source declaration.

### Research Problem

Build a deterministic, non-learning simulator and a unified online policy for all canonical scenes. The policy must jointly choose which queued report the base station services, each robot's fallback motion, and whether each robot reports its new observation after moving. It must use only the local robot information and base-station information available at the relevant decision boundary. The objective is to confirm the source early and reliably while controlling uplink traffic and the age of fused information. The resulting method must address the temporal coupling between motion, sampling, report delay and loss, queue service, source estimation, delayed commands, and the multi-robot support window.

### Experimental Setting and Constraints

#### Canonical scenes and odor field

Each scene uses integer coordinates on the `12 x 12` grid `{0,...,11}^2`, four robots numbered `0,...,3`, and 48 slots `t=0,...,47`. The scene order and fixed environment parameters are:

| scene | source | robot starting positions | wind | A | beta |
|---|---|---|---|---:|---:|
| `crosswind_plume` | `[9,6]` | `[[0,0],[0,11],[3,5],[11,2]]` | `[1,0]` | 12 | 0.18 |
| `sheltered_plume` | `[3,8]` | `[[0,0],[11,0],[2,10],[10,11]]` | `[0,-1]` | 14 | 0.12 |
| `split_plume` | `[8,7]` | `[[0,1],[1,11],[10,0],[11,10]]` | `[1/sqrt(2),1/sqrt(2)]` | 11 | 0.16 |
| `wall_source` | `[10,2]` | `[[0,2],[0,9],[5,0],[8,11]]` | `[-1,0]` | 13 | 0.20 |
| `weak_signal` | `[2,9]` | `[[0,0],[11,1],[1,11],[10,10]]` | `[1/sqrt(2),-1/sqrt(2)]` | 7 | 0.24 |

For scene `s`, source `p_s`, wind `w_s`, and grid position `p`, the concentration is

`C_s(p) = A_s/(1+||p-p_s||_2) * exp(-beta_s*max(0,w_s dot (p-p_s)))`.

The two-component gradient is deterministic. At an interior coordinate, use the centered difference `g_x=(C(x+1,y)-C(x-1,y))/2` and likewise for `g_y`. At coordinate 0 use the forward difference; at coordinate 11 use the backward difference. All concentration and gradient calculations use ordinary double-precision `sqrt` and `exp` semantics. The source position, scene parameters, and current or future link results are environment truth and are not policy inputs. Before slot 0, each robot observes the concentration and gradient at its starting position.

The five actions are `north`, `east`, `south`, `west`, and `stay`, with displacements `[0,1]`, `[1,0]`, `[0,-1]`, `[-1,0]`, and `[0,0]`, respectively. Source confirmation is defined separately below.

#### Reports, queue, and fixed fusion

The base station is at `[6,6]`. A report generated by robot `r` after movement in slot `t` contains that robot's post-movement integer position, concentration, and gradient. Report numbering resets in each scene: reports are assigned IDs `r0,r1,...` in generation order, with robots considered in increasing number within a slot. Let `s` be the zero-based canonical scene index and let `d` be the Manhattan distance from the generation position to `[6,6]`.

A report is `dropped` if `d>8` or `(3*t+5*r+7*s+d) mod 11` is in `{0,1}`. Otherwise its delay is `1+((t+r+s+d) mod 3)` and its arrival slot is `t+delay`. It is `late` if that arrival is greater than 47, and `delivered` otherwise. Only delivered reports enter the queue, at the beginning of their arrival slot. The queue has no capacity limit; reports remain until serviced or the horizon ends. The service decision is either `null` or the ID of one report in the service-before queue. At most one report is serviced per slot, and a report is serviced at most once. Queue IDs are recorded in `(arrival_t,numeric_report_id)` order.

The source estimate starts at `[6.0,6.0]`. The base station's position estimate for each robot starts at that robot's public starting position. Servicing a report updates the corresponding robot-position estimate and replaces that robot's most recently serviced report. In a slot with a service, the fusion set contains, in robot order, each robot's most recently serviced report satisfying `t-generated_t<=3`. For report `i` in this set, define

`a_i=t-generated_t`, `z_i=p_i+2*g_i/(||g_i||_2+1e-9)`, and `w_i=c_i*clip(1-a_i/3,0,1)`.

If the sum of positive weights is nonzero, the new source estimate is `sum_i(w_i*z_i)/sum_i(w_i)`, clipped component-wise to `[0,11]`; otherwise it remains unchanged. If no report is serviced, the fusion set is empty and the estimate remains unchanged.

#### Downlink commands and robot movement

Exactly one downlink command is generated whenever one report is serviced, and no command is generated on a null service. Command numbering also resets in each scene, with consecutive IDs `c0,c1,...`. Using the current base-station robot-position estimates, the target is the robot with greatest Euclidean distance from the updated source estimate; a distance tie selects the lower robot number. At the target's estimated position, evaluate all five action destinations and choose the action whose destination, after component-wise clipping to the grid, has minimum Euclidean distance to the source estimate. Both comparisons use squared Euclidean distance. Let `d_max` be the largest robot distance; the target is the lowest-numbered robot with distance at least `d_max-1e-12`. Let `d_min` be the smallest action-destination distance; the command uses the first action with distance at most `d_min+1e-12` in `north,east,south,west,stay` order. The command stores that action and the fusion report IDs.

A command generated in slot `u` arrives at its target at the beginning of slot `u+1`. The newest arrived command replaces that robot's stored command. A stored command is effective while its age `t-u` is in `1..3`; it supplies the robot's executed action in every such slot. Otherwise the robot executes the policy's submitted fallback action. There is no downlink loss.

Motion is simultaneous. First form each destination. An action leaving the grid makes that robot stay and sets `blocked=true`; blocked robots do not participate as movers in collision tests. A non-blocked, non-stay mover collides if its destination is another robot's pre-movement position, or if at least two movers select the same otherwise unoccupied destination. Every colliding mover stays and has `collision=true`. Other moves succeed. A `stay` action has both flags false. This rule keeps all positions distinct.

After movement, each robot samples its new concentration and gradient and then chooses its Boolean `send` decision. At most 36 reports may be generated in a scene. For every slot `t`, at most three reports may be generated over slots `max(0,t-3),...,t`; each robot generates at most one report in a slot. Within a slot, send decisions are applied in robot order. A reusable scheduler may use the remaining common report budget, earlier robot decisions in that slot, and past send counts, but a robot's report trigger may use only that robot's observed history rather than unreported observations of other robots.

#### Confirmation, event order, and information boundary

At the end of slot `t`, a report is a current support report exactly when all of the following hold: it was generated in `max(0,t-4),...,t`; it has been serviced by `t`; its service occurred no more than four slots after generation; and its generation position has Manhattan distance at most 2 from the true source. All qualifying IDs are recorded in numeric report-ID order.

The source becomes confirmed at the end of the first slot satisfying both conditions:

- at least one robot's post-movement position has Manhattan distance at most 1 from the source, and  that robot has `collision=false` in the current and preceding two available slots;
- current support reports come from at least two different robots.

Once true, confirmation remains true. All 48 slots are still executed and recorded. Reports arriving after slot 47 do not enter the queue and cannot affect confirmation.

Each slot has this exact order: enqueue delivered uplink arrivals; install downlink commands created one slot earlier; expose the service-before queue, robot states, and observations; choose one service ID and four fallback actions; service the report, update fixed fusion state, and create a command; select effective commands or fallbacks; resolve simultaneous motion; sample post-movement local observations; choose the four send decisions in robot order; derive report link events; evaluate support and confirmation; record the slot.

At the pre-movement decision boundary, each local fallback rule sees only that robot's position, current local concentration and gradient, its effective downlink command if any, its own history, and shared resource counters. The base-station service rule sees only the service-before queue, previously serviced reports, source and robot-position estimates, past decisions, and remaining budget. A send trigger additionally sees its own post-movement observation. No decision may inspect the source, scene parameters, another robot's unreported observation, an unarrived report, the current send's link outcome, or future state or link events. One reusable procedure must generate decisions in every scene; scene-, robot-, regime-, or absolute-slot action tables are prohibited.

The decision fields in `decisions` are the submitted choices at their stated boundaries. `queue_report_ids`, pre-movement robot state, local observations, and active command fields are the feedback already visible at those boundaries. Executed actions, post-movement state, fusion state, new command fields, support IDs, and confirmation are post-event evidence. The event order above is the authoritative interpretation.

#### Result contract and metrics

`results.json` is strict JSON with exactly `{"scenarios":[...]}`. The array contains the five scenes in canonical order. Each scene object has exactly `scenario`, `decisions`, `robot_trace`, and `base_trace`.

`decisions` contains exactly 48 records in `t=0,...,47` order. Each has exactly `t`, `service_report_id`, and `robots`. `service_report_id` is a string report ID or `null`. `robots` contains four records in robot order, each with exactly `robot` (integer), `fallback_action` (one of the five action strings), and `send` (Boolean). Service and fallback fields are pre-movement decisions; `send` is the post-sampling decision.

`robot_trace` contains exactly 192 records in `(t,robot)` order. Each has exactly `t`, `robot`, `position`, `concentration`, `gradient`, `command_id`, `command_age`, `executed_action`, `post_position`, `blocked`, and `collision`. Positions are two-integer grid arrays. Concentration is a finite nonnegative number and gradient is a two-number finite array. `command_id` is a command ID or `null`; `command_age` is the corresponding integer in `1..3` or `null`, and both are null together. The action is one of the five strings and both flags are Boolean. State and observations are from the pre-movement boundary; action, post-position, and flags are post-event evidence.

`base_trace` contains exactly 48 records in slot order. Each has exactly `t`, `queue_report_ids`, `fusion_report_ids`, `estimate`, `command_id`, `command_target`, `command_action`, `support_report_ids`, and `confirmed`. All ID collections are arrays of unique strings in the orders defined above. `estimate` is a two-number finite array in `[0,11]^2`. The three command fields are all null when there is no command; otherwise they are a command ID, an integer robot in `0..3`, and an action string. `confirmed` is Boolean. Reports and commands are fixed-model events derived from the submitted decisions and are not submitted as redundant event tables.

All integer fields reject Booleans. Comparisons between submitted numeric evidence and replayed values use absolute tolerance `1e-6`; the command tie threshold remains `1e-12` as defined above. The grader independently replays report IDs and payloads, status and arrival, queue service, fusion, commands, movement, observations, support, and confirmation. No self-reported metric is accepted.

`primary_metrics_1` is the fraction of the five scenes that confirm the source. `primary_metrics_2` is the mean confirmation-time utility: a confirmed scene receives `max(0,1-t_confirm/47)`, where `t_confirm` is its first confirmed slot, and an unconfirmed scene receives 0. `auxiliary_metrics_1` is the mean over scenes of `clip(1-n_reports/36,0,1)`. `auxiliary_metrics_2` is the mean over all scene slots of `max(0,1-a/3)` for the report serviced in that slot when it has positive fusion weight, and 0 for a null service or a zero-weight serviced report. Higher is better for every metric. The normalized task performance is `(8*primary_metrics_1+7*primary_metrics_2+3*auxiliary_metrics_1+2*auxiliary_metrics_2)/20`. Metrics are scored only when all validity checks pass.
